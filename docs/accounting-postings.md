# سند طراحی Postingهای دفتر کل چندواحدی

**تسک:** BE-029
**وضعیت:** تأییدشده در 2026-08-05؛ baseline پیاده‌سازی فاز ۱.
**دامنه:** فاز ۱؛ مرجوعی B2B عمداً در این سند وجود ندارد.

## ۱. اصل مدل

دفتر کل یک دفتر برداری است، نه دفتری که همه‌چیز را پیش از ثبت به ریال یا
گرم تبدیل کند. هر entry یک مقدار صحیحِ علامت‌دار در دقیقاً یک بُعد دارد:

| بعد | واحد ذخیره‌سازی | نمونه |
| --- | --- | --- |
| `RIAL` | `bigint` ریال | `"250000000"` |
| `GOLD` | `bigint` میلی‌گرم طلای خالص ۱۰۰۰ | `"5000"` |
| `COIN:<coinTypeId>` | تعداد صحیح سکه | `"1"` |
| `SILVER` | `bigint` میلی‌گرم نقرهٔ خالص ۱۰۰۰ | فقط مدل؛ بدون جریان عملیاتی فاز ۱ |

`quantity` در storage و قرارداد API رشته‌ی صحیح علامت‌دار است. علامت ثابت
است: **بدهکار = مثبت** و **بستانکار = منفی**. نوع حساب فقط معنی مانده را
تعیین می‌کند؛ برای یک entry فیلد جداگانه‌ی debit/credit ساخته نمی‌شود.

ناوردای دیتابیس برای هر `ledger_transaction` چنین است:

```text
برای هر dimension_id: SUM(ledger_entries.quantity) = 0
```

این ناوردا با constraint trigger از نوع `DEFERRABLE INITIALLY DEFERRED` اعمال
می‌شود، نه با جمع‌زدن در کد برنامه. بنابراین یک سند چندبعدی می‌تواند هم‌زمان
ریال و طلا و چند نوع سکه داشته باشد، اما جمع **هر بُعد جداگانه** صفر است.

هیچ entry سکه‌ای به وزن طلا تبدیل نمی‌شود. نرخ، ارزش ذاتی و حباب فقط snapshot
سند/گزارش هستند؛ خود entry سکه فقط تعداد همان `coin_type` را نگه می‌دارد.

## ۲. snapshot و منبع سند

هر `ledger_transaction` یک `source_type` بسته و یک `source_id` دارد. در فاز ۱
منبع‌های موردنیاز این سند عبارت‌اند از `OPENING_BALANCE`، `SALES_INVOICE`،
`SECOND_HAND_PURCHASE`، `SETTLEMENT` و `SALES_INVOICE_AMENDMENT`. برای هر
`tenant_id + source_type + source_id` حداکثر یک ledger transaction نهایی ساخته
می‌شود.

هر سند مبدأ، نه خود ledger، snapshotهای زیر را نگه می‌دارد:

- شناسه و مبلغ/زمان مظنه، نرخ تبدیل هر ردیف و نسخه‌ی تنظیمات مؤثر؛
- وزن خالص محاسبه‌شده، عیار و جزئیات نسخه‌ی کالا یا نوع سکه؛
- مبلغ نهاییِ گرد‌شده فقط یک‌بار با `roundHalfUp` در `core-calc`؛
- برای مرجوعی B2C، شناسه‌ی فاکتور اصلی و breakdown اختلاف، بدون تغییر آن فاکتور.

metadata entry فقط شناسه‌ی snapshot و اطلاعات ردیابی را دارد؛ پول و وزن در JSON
همیشه رشته هستند. هیچ گزارش تاریخی برای ساختن این داده‌ها مظنه‌ی امروز را
نمی‌خواند.

## ۳. حساب‌های سیستمی لازم برای BE-031

نام نهایی و codeها داده‌ی seed نسخه‌دار tenant هستند؛ کلیدهای زیر فقط قرارداد
معنایی postingها هستند.

| system key | نقش | بعدهای مجاز |
| --- | --- | --- |
| `CASH` / `BANK` | دارایی نقد و بانک | `RIAL` |
| `INVENTORY_JEWELRY` | موجودی مصنوعات برحسب طلای خالص | `GOLD` |
| `INVENTORY_MELTED_GOLD` | موجودی آبشده برحسب طلای خالص | `GOLD` |
| `INVENTORY_COIN:<coinTypeId>` | موجودی هر نوع سکه | فقط بعد همان سکه |
| `PARTY_RECEIVABLE:<partyId>` | طلب از شخص | `RIAL`، `GOLD` یا بعد سکه؛ جدا و بدون اختلاط در یک line |
| `PARTY_PAYABLE:<partyId>` | بدهی به شخص | `RIAL`، `GOLD` یا بعد سکه |
| `OPENING_EQUITY` | طرف مقابل افتتاحیه | هر بعد فعال |
| `SALES_REVENUE` | درآمد فروش | `RIAL` یا `GOLD` برای همان نوع اعتبار فروش |
| `COGS_JEWELRY` / `COGS_COIN` | خروج کالای فروخته‌شده | `GOLD` / بعد همان سکه |
| `PURCHASE_FROM_CONSUMER` | بهای خرید از مصرف‌کننده | `RIAL`، `GOLD` یا بعد سکه |
| `SETTLEMENT_CONVERSION_CLEARING` | طرف مقابل تبدیلِ قفل‌شده بین ابعاد | فقط در سند settlement و دقیقاً همراه snapshot تبدیل |

`SETTLEMENT_CONVERSION_CLEARING` سود، زیان، صندوق یا موجودی نیست. فقط ضلع مقابل
تبدیل میان دو بُعد است تا حذف یک طلب ریالی در برابر دریافت طلا یا سکه، در هر
بُعد صفر بماند. مانده‌ی برداری آن با ردیف‌های settlement و نرخ‌های قفل‌شده قابل
ردیابی است و هرگز با نرخ لحظه‌ای بازنویسی نمی‌شود.

موجودی جزئی زیورآلات در `inventory_movements` برحسب تعداد و `item_id` می‌ماند؛
ledger فقط وزن خالص همان نسخه‌ی کالا را در بعد `GOLD` ثبت می‌کند. آبشده در هر دو
جا میلی‌گرم خالص است. حرکت و entry سکه دقیقاً همان count را دارند.

## ۴. قرارداد اتمیک

هر جریان نهایی در **یک PostgreSQL transaction**، با همان `TenantTransaction`،
به‌ترتیب زیر انجام می‌شود:

1. کنترل Idempotency-Key و قفل/اعتبارسنجی سند مبدأ؛
2. ساخت یا نهایی‌سازی سند مبدأ و snapshotها؛
3. ثبت `inventory_movements` با همان transaction، در صورت اثر موجودی؛
4. ساخت transaction و entryهای دفتر کل با همان transaction؛
5. ثبت audit log و commit؛ constraint trigger در پایان transaction تراز را
   بررسی می‌کند.

rollback هر مرحله، هم movement و هم ledger و هم سند مبدأ را برمی‌گرداند. مسیر
نوشتنی مستقل برای movement یا ledger در این جریان‌ها وجود ندارد. تکرار همان
Idempotency-Key همان پاسخ ثبت نخست را برمی‌گرداند و unique منبع ledger نیز یک
لایه‌ی دفاعی دوم است.

## ۵. سناریوهای مرجع

همه‌ی اعداد زیر صرفاً **مثال snapshot** هستند، نه تنظیم یا نرخ هاردکد. `+` بدهکار
و `−` بستانکار است. جمع هر گروهِ بُعد در ستون آخر صفر است.

### ۵.۱ موجودی افتتاحیه

سند `OPENING_BALANCE` شامل دو قطعه زیورآلات از یک نسخه با وزن خالص `"7500"`
میلی‌گرم برای هر قطعه، `"5000"` میلی‌گرم آبشده و `"3"` سکه‌ی نوع مشخص است.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `GOLD` | `INVENTORY_JEWELRY` | `+15000` |
| `GOLD` | `INVENTORY_MELTED_GOLD` | `+5000` |
| `GOLD` | `OPENING_EQUITY` | `-20000` |
| `COIN:<new-bahar>` | `INVENTORY_COIN:<new-bahar>` | `+3` |
| `COIN:<new-bahar>` | `OPENING_EQUITY` | `-3` |

اثر موجودی: زیورآلات `+2` قطعه، آبشده `+5000` میلی‌گرم و همان نوع سکه `+3`.
جمع `GOLD` برابر صفر و جمع بعد سکه هم صفر است. این دقیقاً مدلی است که BE-028
پس از BE-034 در یک transaction پیاده می‌کند.

### ۵.۲ فروش نقدی زیورآلات

یک قطعه با وزن خالص `"5000"` میلی‌گرم فروخته می‌شود. مبلغ نهایی snapshot
`"250000000"` ریال است؛ این مثال نرخ نمایش `"50000000"` ریال برای هر گرم ۱۰۰۰
را نیز در invoice نگه می‌دارد.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `CASH` | `+250000000` |
| `RIAL` | `SALES_REVENUE` | `-250000000` |
| `GOLD` | `COGS_JEWELRY` | `+5000` |
| `GOLD` | `INVENTORY_JEWELRY` | `-5000` |

اثر موجودی: movement زیورآلات همان `item_id` برابر `-1`؛ اثر مانده‌ی شخص: ندارد.
جمع ریال و طلا هر کدام صفر است.

### ۵.۳ فروش نسیهٔ زیورآلات

همان کالا با مبلغ snapshot `"250000000"` ریال بدون پرداخت فروخته می‌شود.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `PARTY_RECEIVABLE:<customer>` | `+250000000` |
| `RIAL` | `SALES_REVENUE` | `-250000000` |
| `GOLD` | `COGS_JEWELRY` | `+5000` |
| `GOLD` | `INVENTORY_JEWELRY` | `-5000` |

اثر موجودی `-1` قطعه و مانده‌ی مشتری `+250000000` ریال است. اگر فروشنده
اعتبار را **طلا** انتخاب کند، فقط زوج ریالی نخست با
`PARTY_RECEIVABLE +5000` و `SALES_REVENUE -5000` در بعد `GOLD` جایگزین می‌شود؛
بخش موجودی تغییر نمی‌کند. هر فاکتور فقط یک بُعد اعتبار انتخاب می‌کند و snapshot
ریالی آن برای گزارش حفظ می‌شود.

### ۵.۴ فروش سکه

یک سکه‌ی `COIN:<new-bahar>` با قیمت بازار snapshot `"500000000"` ریال نقدی
فروخته می‌شود.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `CASH` | `+500000000` |
| `RIAL` | `SALES_REVENUE` | `-500000000` |
| `COIN:<new-bahar>` | `COGS_COIN` | `+1` |
| `COIN:<new-bahar>` | `INVENTORY_COIN:<new-bahar>` | `-1` |

movement همان نوع سکه `-1` است؛ هیچ entry طلایی برای آن ساخته نمی‌شود. ارزش
ذاتی و حبابِ سکه‌ی بانک مرکزی فقط snapshot گزارش است و اثر مانده‌ی شخص ندارد.

### ۵.۵ خرید طلای دست‌دوم از مصرف‌کننده

وزن ناخالص `"1000"` میلی‌گرم با عیار snapshot `740`، پس وزن خالص
`"740"` میلی‌گرم است. مبلغ خرید امروز `"37000000"` ریال نقدی است.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `PURCHASE_FROM_CONSUMER` | `+37000000` |
| `RIAL` | `CASH` | `-37000000` |
| `GOLD` | `INVENTORY_MELTED_GOLD` | `+740` |
| `GOLD` | `PURCHASE_FROM_CONSUMER` | `-740` |

movement آبشده `+740` میلی‌گرم است؛ موجودی مصنوعات افزایش نمی‌یابد. اگر پرداخت
نشد، فقط `CASH -37000000` با `PARTY_PAYABLE:<seller> -37000000` جایگزین می‌شود.

### ۵.۶ خرید سکه از مصرف‌کننده

یک سکه‌ی مشخص از مصرف‌کننده با مبلغ snapshot `"500000000"` ریال نقدی خریده
می‌شود.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `PURCHASE_FROM_CONSUMER` | `+500000000` |
| `RIAL` | `CASH` | `-500000000` |
| `COIN:<new-bahar>` | `INVENTORY_COIN:<new-bahar>` | `+1` |
| `COIN:<new-bahar>` | `PURCHASE_FROM_CONSUMER` | `-1` |

movement همان coin type `+1` است. نرخ بازار و مظنه snapshot هستند، اما هیچ وزن
یا حبابی در entry سکه ذخیره نمی‌شود.

### ۵.۷ پرداخت ریالی روی مانده‌ی شخص

مشتری `"100000000"` ریال از طلب خود را نقداً می‌پردازد.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `CASH` | `+100000000` |
| `RIAL` | `PARTY_RECEIVABLE:<customer>` | `-100000000` |

اثر موجودی ندارد؛ مانده‌ی ریالی مشتری به اندازه‌ی همان مبلغ کم می‌شود و جمع
بعد ریال صفر است.

### ۵.۸ پرداخت با طلا روی طلب ریالی

مشتری طلب ریالی `"250000000"` را با `"5000"` میلی‌گرم طلای خالص می‌پردازد.
نرخ تبدیل snapshot این ردیف `"50000000"` ریال برای هر گرم ۱۰۰۰ است.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `GOLD` | `INVENTORY_MELTED_GOLD` | `+5000` |
| `GOLD` | `SETTLEMENT_CONVERSION_CLEARING` | `-5000` |
| `RIAL` | `PARTY_RECEIVABLE:<customer>` | `-250000000` |
| `RIAL` | `SETTLEMENT_CONVERSION_CLEARING` | `+250000000` |

movement آبشده `+5000` میلی‌گرم است. تبدیل فقط با snapshot همین settlement
توضیح داده می‌شود؛ نه طلای فرضی در storage ساخته می‌شود و نه نرخ امروز خوانده
می‌شود. اگر طلب خودِ مشتری طلا باشد، clearing لازم نیست: inventory طلا `+5000`
و receivable طلا `-5000` ثبت می‌شود.

### ۵.۹ پرداخت با سکه روی طلب ریالی

مشتری طلب `"500000000"` ریالی را با یک `COIN:<new-bahar>` می‌پردازد. قیمت بازار
و مظنه‌ی هر دو در settlement snapshot شده‌اند.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `COIN:<new-bahar>` | `INVENTORY_COIN:<new-bahar>` | `+1` |
| `COIN:<new-bahar>` | `SETTLEMENT_CONVERSION_CLEARING` | `-1` |
| `RIAL` | `PARTY_RECEIVABLE:<customer>` | `-500000000` |
| `RIAL` | `SETTLEMENT_CONVERSION_CLEARING` | `+500000000` |

movement همان نوع سکه `+1` است. هیچ تبدیل سکه به گرم در ledger یا inventory رخ
نمی‌دهد. برای طلب سکه‌ای هم‌نوع، دو entry مستقیم inventory `+1` و receivable
`-1` کافی است.

### ۵.۱۰ تسویهٔ ترکیبی

طلب ریالی مشتری `"350000000"` است: `"100000000"` ریال نقد، `"2000"`
میلی‌گرم طلا با نرخ snapshot `"50000000"` ریال/گرم و یک سکه‌ی گرمی با ارزش
snapshot `"150000000"` ریال دریافت می‌شود.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `CASH` | `+100000000` |
| `RIAL` | `PARTY_RECEIVABLE:<customer>` | `-350000000` |
| `RIAL` | `SETTLEMENT_CONVERSION_CLEARING` | `+250000000` |
| `GOLD` | `INVENTORY_MELTED_GOLD` | `+2000` |
| `GOLD` | `SETTLEMENT_CONVERSION_CLEARING` | `-2000` |
| `COIN:<gerami>` | `INVENTORY_COIN:<gerami>` | `+1` |
| `COIN:<gerami>` | `SETTLEMENT_CONVERSION_CLEARING` | `-1` |

همه‌ی lineها یک settlement و یک transaction هستند: جمع ریال `0`، جمع طلا `0`
و جمع بعد سکه `0` است. failure هر خط کل سند را rollback می‌کند.

### ۵.۱۱ مرجوعی B2C متصل به فاکتور

این **برگشت فروش نیست**. مشتری کالایی را که قبلاً در فاکتور `INV-...` خریده،
امروز به‌صورت طلای دست‌دوم می‌فروشد. وزن `"1000"` میلی‌گرم با عیار مؤثر
snapshot `740`، وزن خالص `"740"` میلی‌گرم و مبلغ خرید امروز `"37000000"` ریال
است. مبلغ خرید اولیه فقط برای breakdown نمایش داده می‌شود و در posting دخالت
ندارد.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `PURCHASE_FROM_CONSUMER` | `+37000000` |
| `RIAL` | `CASH` | `-37000000` |
| `GOLD` | `INVENTORY_MELTED_GOLD` | `+740` |
| `GOLD` | `PURCHASE_FROM_CONSUMER` | `-740` |

movement آبشده `+740` است، نه movement مصنوعات. سند مبدأ یک
`SECOND_HAND_PURCHASE` با `originInvoiceId` است؛ فاکتور اصلی و ledger قبلی
هرگز update یا delete نمی‌شوند. اجرت قبلی سوخته است و در این خرید بازگشت ندارد.

### ۵.۱۲ اصلاح فاکتور با سند تفاضلی

فاکتور نهاییِ قبلی شامل `"5000"` میلی‌گرم و `"250000000"` ریال بوده است. نسخه‌ی
جدیدِ snapshot‌شده `"4000"` میلی‌گرم و `"210000000"` ریال است؛ پس اصلاح، بازگشت
`"1000"` میلی‌گرم به موجودی و refund `"40000000"` ریال است.

| بعد | حساب | quantity |
| --- | --- | ---: |
| `RIAL` | `SALES_REVENUE` | `+40000000` |
| `RIAL` | `CASH` | `-40000000` |
| `GOLD` | `INVENTORY_JEWELRY` | `+1000` |
| `GOLD` | `COGS_JEWELRY` | `-1000` |

این transaction تنها اختلاف دو نسخه است. اگر پرداخت اولیه نسیه بوده باشد،
`CASH -40000000` با `PARTY_RECEIVABLE:<customer> -40000000` جایگزین می‌شود.
هر دو snapshot نسخه روی سند اصلاح نگه داشته می‌شوند؛ نرخ جاری بازار برای
محاسبه‌ی گذشته استفاده نمی‌شود.

## ۶. پیامدهای پیاده‌سازی تسک‌های بعدی

1. **BE-030:** ابعاد پایه‌ی tenant و بعد مستقل هر `coin_type` فعال را می‌سازد.
   `inventory_movements.dimension_id` بعد از آن کلید خارجی و non-null می‌شود.
2. **BE-031:** حساب‌های جدول بخش ۳ را seed می‌کند؛ حساب شخص فقط در tenant خود
   و با party همان tenant ساخته می‌شود.
3. **BE-032:** ledger transaction، entryهای signed، یکتایی منبع و RLS را ایجاد
   می‌کند؛ entryها append-only هستند.
4. **BE-033:** constraint trigger تراز برداری را در دیتابیس اعمال می‌کند.
5. **BE-034:** تنها API داخلی `postInTransaction` را می‌سازد؛ source snapshot و
   همه‌ی dimensionها پیش از commit اعتبارسنجی می‌شوند.
6. **بازگشت به BE-028:** endpoint افتتاحیه یک header/line source مشخص می‌سازد و
   همان `TenantTransaction` را به inventory و `LedgerPostingService` می‌دهد.
   در نتیجه retry فقط یک سند، movement و ledger transaction خواهد داشت.
