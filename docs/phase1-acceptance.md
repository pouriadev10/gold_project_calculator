# تست پذیرش فاز ۱ — FE-110

> **وضعیت: شواهد خودکار کامل؛ هفته‌ی پایلوت واقعی هنوز اجرا نشده.** معیار اصلی FE-110 این است که «یک خرده‌فروش
> بتواند یک هفته همه معاملات فاز ۱ را در سیستم ثبت کند» — این را فقط خودِ خرده‌فروش روی API ِ واقعی می‌تواند
> نشان دهد. بخش ۱ و ۲ نشان می‌دهند هر سناریو و هر معیار تجربه کجا و چطور خودکار سنجیده می‌شود؛ بخش ۴ پروتکل و
> دفتر روزانه‌ی همان هفته است. FE-110 (مثل FE-086) وقتی تیک می‌خورد که دفتر هفته پر شده و معیار خروج برقرار باشد.

**آخرین اجرای خودکار:** ۱۴۰۵/۰۷/۲۵ (۲۰۲۶-۱۰-۱۷) · شاخه‌ی `dev_pouria` · `pnpm gate:frontend` و `pnpm --filter @gold/web test:e2e`
(۲۳ مرحله، روی ۳۶۰×۸۰۰ لمسی و ۱۴۴۰×۹۰۰ ماوس، هر دو سبز).

**مرز این شواهد:** E2E روی **بیلد production** اجرا می‌شود ولی پشتش API ِ ساختگی قراردادمحور است (handlerهای MSW
در Node، با `contract-gate.ts` که هر بدنه را با schema ِ `packages/contracts` می‌سنجد) — نه سرور NestJS و
PostgreSQL ِ واقعی. منطق سرور (دفتر کل، ناوردای مجموع صفر، شماره‌ی بی‌شکاف، RLS) آزمون‌های بک‌اند خودش را دارد؛
مسیر کامل «مرورگر ← API ِ واقعی ← دیتابیس» در این محیط (بدون Docker) اجرا نشده و همان چیزی است که هفته‌ی پایلوت
باید ثابت کند.

## ۳. شکاف‌های شناخته‌شده (پیش از هفته‌ی پایلوت)

1. **API ِ واقعی سرتاسری آزموده نشده.** حالت `VITE_API_MODE=real` (FE-106a) وجود دارد، ولی در این محیط Docker
   نیست. پیش از روز اول، مسیر بخش ۱ یک بار روی API ِ واقعی دستی اجرا شود ([راهنمای اجرا](../apps/web/README.md)).
2. **ساخت کاربر endpoint ندارد.** کاربر اول با SQL ساخته می‌شود (README، بخش اتصال API).
3. **دستگاه اندروید واقعی** — FE-086 ([پروتکل](android-device-test.md)) هنوز اجرا نشده؛ INP و لمس واقعی آنجا سنجیده می‌شوند.
4. **۱۵ ثانیه‌ی خودکار، زمان انسان نیست.** راننده با فاصله‌ی ۵۰ms تایپ می‌کند و صبرهای ثابت دارد؛ عدد بالا یعنی
   سیستم خودش بیش از ~۸ ثانیه از بودجه را نمی‌گیرد. زمان واقعی را دفتر بخش ۴ ثبت می‌کند.
